# 온톨로지 구성·관리

온톨로지 구성을 요청하면 프로젝트 루트의 `ONTOLOGY.yaml`에 프로젝트 구조를 이해하고 자료를 찾는 데 필요한 개념·관계·소스를 기록한다. 온톨로지는 일반 프로젝트 문서에 더해 별도의 사용자 통제 절차를 적용하는 특수 문서다.

## 참조자료

- [구조 템플릿](ONTOLOGY.template.yaml): 항목과 필수·선택 속성을 확인할 때 읽는다.
- [작성 예시](ONTOLOGY.example.yaml): 태그, 소스 참조, 동기화를 작성하는 방식을 확인할 때 읽는다. 예시의 개념·소스·저장 방식·개수는 프로젝트의 필수 구성이 아니다.

참조자료는 작성 지침이다. 프로젝트 정본을 덮어쓰거나 스킬과 프로젝트 사이에서 자동 동기화하지 않는다.

## 프로젝트에 맞게 구성하기

1. 사용자 요청, 기존 온톨로지, 에이전트 지침, 프로젝트 문서와 실제 저장 구조를 확인한다. 현재 프로젝트 작업에 사용하는 정본·참고본·근거 자료를 식별하고, 실제 파일·연결 정보·API 응답에서 확인한 위치로 초안을 만든다. 존재하지 않는 서비스·식별자·동기화 방법을 추정해 채우지 않는다.
2. 사용자가 직접 지정한 내용은 그 범위에서 반영한다. 그 밖의 신규 구성과 변경은 아래 사용자 통제 절차에 따라 구체적인 초안을 제시한다.
3. 승인된 내용만 정본에 반영한다. 도우미가 생성한 빈 목록은 출발점이며, 구성 요청이 완료된 결과로 보고하지 않는다.
4. 기존 정본이 있으면 형식과 내용을 먼저 존중한다. 새 템플릿으로의 이관이나 전체 재작성은 사용자가 구체적으로 요청하거나 변경안을 승인한 경우에만 수행한다.
5. 에이전트 지침에 정본 위치·참조 시점·사용자 통제 규칙을 연결한다. 프로젝트에 용어 문서가 있으면 이름·한글명·의미를 맞추고, 결정 기록 문서가 있으면 승인된 주요 변경의 이유와 결정을 기록한다. 해당 문서의 이름·형식·위치는 프로젝트 관례를 따른다.

## 구조와 확장

- 기본 묶음은 `개념[]`, `관계[]`, `소스[]`다. 종류와 개수는 프로젝트에 맞게 정한다.
- `이름`은 영문 snake_case 식별자이고 `한글명`은 필수다. 개념 이름과 최상위 소스 이름은 각 목록에서 고유하게 정한다.
- 소스는 DB·문서·파일 등 실제 데이터 단위로 정의한다. 개념 내부 소스의 `이름`은 최상위 소스의 `이름`을 그대로 참조한다. 별도의 `소스명`을 만들지 않는다.
- `태그`는 소스의 역할을 나타낸다. 예: `정본`, `우선 탐색 대상`, `참고본`. 한 소스가 여러 역할을 가질 수 있으며, 같은 정보 범위의 정본이 충돌하지 않게 한다.
- 최상위 소스의 `소스정보`에 실제 위치와 식별자를 반드시 기록한다. 이름이나 사용방법만으로 위치를 대신하지 않는다. 개념 내부 소스는 이 정의를 참조하고 해당 개념의 범위·필드·조회 조건을 더한다.
- 로컬 파일은 실제 파일 경로와 기준 경로 또는 절대 경로를 기록한다. 파일 묶음은 경로 패턴과 치환할 식별자의 의미를 명시한다.
- Notion DB는 확인한 DB 주소와 `database_id`, 조회에 사용하는 `data_source_id`를 구분해 기록한다. 둘을 같은 ID라고 추정하지 않는다. 고정 문서를 참조하면 해당 페이지 주소·ID와 필요한 본문 섹션도 밝힌다.
- 링크로 결정되는 자료는 실제 URL·파일 ID가 저장된 문서 경로·섹션·필드를 명시한다. 모든 자료에 하나의 고정 ID가 있는 것처럼 값을 만들지 않는다. 위치를 확인하지 못했으면 그 상태를 알리고 필요한 근거를 확인한다.
- 관계의 주체·대상은 개념 이름을 참조하고, 관계는 방향이 분명한 동사로 적는다. 대상이 여러 개면 관계를 나눠 적는다.
- 동기화는 필요한 경우에만 원본·대상·방법을 간단히 기록한다. 원본과 대상은 해당 개념의 소스 목록에 있어야 한다. 문서에 절차를 기록하는 것과 실제 동기화 작업을 실행하는 것은 구분한다.
- 프로젝트에 필요한 태그·속성·하위 구조를 확장할 수 있다. 기존 이름과 참조의 의미를 유지하며, 확장도 사용자 통제 절차를 따른다.
- 템플릿의 `?`는 생략 가능한 속성 표기다. 실제 문서에서는 사용하는 키의 `?`를 제거하고 불필요한 항목을 생략한다. `<...>` 자리표시자를 정본의 확정된 내용으로 남기지 않는다.

## 유형별 필수 위치 정보

최상위 `소스[].소스정보`는 필수이며 실제 문서에서 빈 사전으로 남기지 않는다. 이름·서비스명·용도 설명만으로 위치를 대신하지 않는다. 다음 중 해당 소스 유형에 필요한 정보를 기록한다. 모든 유형을 프로젝트에 구성할 필요는 없다.

| 소스 유형 | 필수 정보 |
| --- | --- |
| 로컬 파일 | 실제 파일 경로. 상대 경로라면 기준 디렉터리도 명시한다. |
| 파일 묶음 | 실제 디렉터리·경로 패턴·변수의 의미. 사용한 파일이 그 패턴에 포함되는지도 확인한다. |
| Notion DB | 확인한 DB URL, `database_id`, 조회에 사용하는 `data_source_id`. |
| Notion 페이지 | 페이지 URL, `page_id`, 필요한 본문 섹션. |
| Drive 파일 | 파일 URL과 `file_id`. 접근 계정이 구분에 필요하면 계정도 적는다. |
| 메일 | 계정, 메시지 URL 또는 메시지 ID. |

고정 위치가 아닌 연결 자료는 실제 URL·ID가 저장된 문서의 경로·섹션·필드까지 특정한다. 확인하지 못한 위치는 추정하거나 예시 값으로 채우지 않는다. 필요한 근거를 확인하거나 사용자에게 확인할 항목을 제시한다. 소스 발견과 위치 확인만으로 등록·변경 동의를 받았다고 간주하지 않는다.

## 사용자 통제

- 온톨로지의 신규 내용과 개념·관계·소스·속성의 추가·수정·삭제, 이름·구조·서식 변경은 사용자가 직접 구체적으로 지정하거나 명시적으로 승인한 범위에서만 반영한다. 오탈자·서식 수정도 예외가 아니다.
- 사용자가 직접 지정하지 않은 변경은 이유, 변경 전후 내용, 영향을 제시하고 동의를 받는다. 동의 전에는 기존 정본을 유지하고, 제안은 대화나 별도 초안에서 검토할 수 있게 한다.
- 무응답, 추정, 새 사실이나 구조의 발견, 일반적인 관리·정리 요청, 과거의 포괄적 위임을 변경 동의로 간주하지 않는다. 승인 범위를 넓히려면 별도 동의를 받는다.
- 이미 구체적으로 요청되거나 승인된 동일 범위에 대해 다시 승인을 요구하지 않는다. 그 범위만 반영하고 프로젝트의 추가 관리 규칙도 지킨다.
- 스킬 실행, 초기화, `--force`, 참조자료 변경은 기존 온톨로지를 덮어쓰거나 자동 정규화하는 근거가 아니다.

## 검증 기준

- **구조**: YAML 문법과 템플릿의 필수 항목을 확인한다. 이름은 목록 안에서 고유하고 한글명이 있으며, 프로젝트 확장 속성은 임의로 금지하지 않는다.
- **참조**: 개념의 소스가 최상위 소스를 가리키고, 관계의 주체·대상이 기존 개념이며 관계가 동사인지 확인한다. 동기화를 썼다면 원본·대상이 해당 개념의 소스인지 확인한다.
- **접근성**: 소스 유형에 맞는 실제 경로·URL·식별자가 있고, 그 정보로 같은 원본을 다시 찾을 수 있는지 확인한다. 자리표시자·예시 값이나 확인하지 않은 위치는 정본에 확정값처럼 두지 않는다.
- **통제**: 정본·참고본의 역할이 모순되지 않고, 변경 내용이 사용자가 지정하거나 승인한 범위에 한정되는지 확인한다.

## 검증 절차

1. 변경 전후를 비교해 요청·승인 범위 밖의 수정이 없는지 확인한다.
2. YAML을 파싱하고 위 구조·참조 기준을 대조한다.
3. 파일 경로는 실제 파일을 확인하고, 외부 소스는 가능한 읽기 전용 조회로 주소·ID를 대조한다. 확인할 수 없는 항목은 미검증으로 남긴다.
4. 검증 결과와 미검증 항목을 보고한다. 발견한 오류는 승인된 범위에서만 고치며, 그 밖의 수정은 별도 변경안으로 제시한다.
