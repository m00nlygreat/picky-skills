# 온톨로지 구성·관리

온톨로지 구성을 요청하면 프로젝트 루트의 `ONTOLOGY.yaml`에 프로젝트 구조를 이해하고 자료를 찾는 데 필요한 개념·관계·소스를 기록한다. 온톨로지는 일반 프로젝트 문서에 더해 별도의 사용자 통제 절차를 적용하는 특수 문서다.

## 참조자료

- [구조 템플릿](ONTOLOGY.template.yaml): 항목과 필수·선택 속성을 확인할 때 읽는다.
- [작성 예시](ONTOLOGY.example.yaml): 태그, 소스 참조, 동기화를 작성하는 방식을 확인할 때 읽는다. 예시의 개념·소스·저장 방식·개수는 프로젝트의 필수 구성이 아니다.

참조자료는 작성 지침이다. 프로젝트 정본을 덮어쓰거나 스킬과 프로젝트 사이에서 자동 동기화하지 않는다.

## 프로젝트에 맞게 구성하기

1. 사용자 요청, 기존 온톨로지, 에이전트 지침, 프로젝트 문서와 실제 저장 구조를 확인한다. 프로젝트에서 쓰는 개념·관계와 실제 데이터 위치를 근거로 초안을 만든다. 존재하지 않는 서비스·식별자·동기화 방법을 추정해 채우지 않는다.
2. 사용자가 직접 지정한 내용은 그 범위에서 반영한다. 그 밖의 신규 구성과 변경은 아래 사용자 통제 절차에 따라 구체적인 초안을 제시한다.
3. 승인된 내용만 정본에 반영한다. 도우미가 생성한 빈 목록은 출발점이며, 구성 요청이 완료된 결과로 보고하지 않는다.
4. 기존 정본이 있으면 형식과 내용을 먼저 존중한다. 새 템플릿으로의 이관이나 전체 재작성은 사용자가 구체적으로 요청하거나 변경안을 승인한 경우에만 수행한다.
5. 에이전트 지침에 정본 위치·참조 시점·사용자 통제 규칙을 연결한다. 프로젝트에 용어 문서가 있으면 이름·한글명·의미를 맞추고, 결정 기록 문서가 있으면 승인된 주요 변경의 이유와 결정을 기록한다. 해당 문서의 이름·형식·위치는 프로젝트 관례를 따른다.

## 구조와 확장

- 기본 묶음은 `개념[]`, `관계[]`, `소스[]`다. 종류와 개수는 프로젝트에 맞게 정한다.
- `이름`은 영문 snake_case 식별자이고 `한글명`은 필수다. 개념 이름과 최상위 소스 이름은 각 목록에서 고유하게 정한다.
- 소스는 DB·문서·파일 등 실제 데이터 단위로 정의한다. 개념 내부 소스의 `이름`은 최상위 소스의 `이름`을 그대로 참조한다. 별도의 `소스명`을 만들지 않는다.
- `태그`는 소스의 역할을 나타낸다. 예: `정본`, `우선 탐색 대상`, `참고본`. 한 소스가 여러 역할을 가질 수 있으며, 같은 정보 범위의 정본이 충돌하지 않게 한다.
- `소스정보`의 키는 실제 소스에 맞게 정의한다. DB ID·파일 경로·본문 섹션·필드·조회 조건 등을 필요한 만큼 기록한다. 템플릿의 위치·범위·조건은 작성 틀이다.
- 관계의 주체·대상은 개념 이름을 참조하고, 관계는 방향이 분명한 동사로 적는다. 대상이 여러 개면 관계를 나눠 적는다.
- 동기화는 필요한 경우에만 원본·대상·방법을 간단히 기록한다. 원본과 대상은 해당 개념의 소스 목록에 있어야 한다. 문서에 절차를 기록하는 것과 실제 동기화 작업을 실행하는 것은 구분한다.
- 프로젝트에 필요한 태그·속성·하위 구조를 확장할 수 있다. 기존 이름과 참조의 의미를 유지하며, 확장도 사용자 통제 절차를 따른다.
- 템플릿의 `?`는 생략 가능한 속성 표기다. 실제 문서에서는 사용하는 키의 `?`를 제거하고 불필요한 항목을 생략한다. `<...>` 자리표시자를 정본의 확정된 내용으로 남기지 않는다.

## 사용자 통제

- 온톨로지의 신규 내용과 개념·관계·소스·속성의 추가·수정·삭제, 이름·구조·서식 변경은 사용자가 직접 구체적으로 지정하거나 명시적으로 승인한 범위에서만 반영한다. 오탈자·서식 수정도 예외가 아니다.
- 사용자가 직접 지정하지 않은 변경은 이유, 변경 전후 내용, 영향을 제시하고 동의를 받는다. 동의 전에는 기존 정본을 유지하고, 제안은 대화나 별도 초안에서 검토할 수 있게 한다.
- 무응답, 추정, 새 사실이나 구조의 발견, 일반적인 관리·정리 요청, 과거의 포괄적 위임을 변경 동의로 간주하지 않는다. 승인 범위를 넓히려면 별도 동의를 받는다.
- 이미 구체적으로 요청되거나 승인된 동일 범위에 대해 다시 승인을 요구하지 않는다. 그 범위만 반영하고 프로젝트의 추가 관리 규칙도 지킨다.
- 스킬 실행, 초기화, `--force`, 참조자료 변경은 기존 온톨로지를 덮어쓰거나 자동 정규화하는 근거가 아니다.

## 확인

반영한 범위의 YAML 문법, 이름의 고유성, 필수 한글명, 개념·소스 참조와 동기화 방향을 확인한다. 관계가 동사인지, 실제 프로젝트 자료로 뒷받침되는지, 요청·승인 범위 밖의 변경이 없는지도 확인한다. 확인 과정에서 발견한 추가 수정은 자동 반영하지 않고 변경안으로 제시한다.
