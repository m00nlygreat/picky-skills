# 온톨로지 구성·관리

프로젝트 루트의 `ONTOLOGY.yaml`에는 구조를 이해하고 자료를 찾는 데 필요한 개념·관계·소스, 정본 위치와 식별자, 조회·동기화 정보를 기록한다. 엔티티를 판단하거나 다룰 때 필요한 세부 기준은 `docs/ontology/<영문 개념 이름>.md`에 둔다.

## 참조자료

- [구조 템플릿](ONTOLOGY.template.yaml): 항목과 필수·선택 속성을 확인할 때 읽는다.
- [작성 예시](ONTOLOGY.example.yaml): 태그, 소스 참조, 동기화, 관계 작성 방식을 확인할 때 읽는다. 예시의 개념·소스·저장 방식·개수는 프로젝트의 필수 구성이 아니다.
- 개념별 명세를 작성하거나 갱신할 때는 [엔티티 명세 안내](entity-spec.md)를 읽는다.

참조자료는 작성 지침이다. 프로젝트 정본을 덮어쓰거나 스킬과 프로젝트 사이에서 자동 동기화하지 않는다.

## 프로젝트에 맞게 구성하기

1. 사용자 요청과 에이전트 지침을 확인하고 기존 온톨로지에서 대상 개념·관계·소스를 찾는다. 새 구성이 필요한 항목은 실제 파일이나 API 응답으로 저장 위치를 확인한다.
2. 사용자가 직접 지정한 내용은 그 범위에서 반영한다. 그 밖의 신규 구성과 변경은 아래 사용자 통제 절차에 따라 구체적인 초안을 제시한다.
3. 승인된 내용만 정본에 반영한다. 도우미가 생성한 빈 목록은 출발점이며, 구성 요청이 완료된 결과로 보고하지 않는다.
4. 기존 정본이 있으면 형식과 내용을 먼저 존중한다. 새 템플릿으로의 이관이나 전체 재작성은 사용자가 구체적으로 요청하거나 변경안을 승인한 경우에만 수행한다.
5. 설치·구축을 마치기 전에 [초기화 절차](#초기화)에 따라 `AGENTS.md`에 정본 위치·참조 시점·사용자 통제 규칙을 기록하고 실제로 존재하는 엔티티 명세를 연결한다. 프로젝트에 용어 문서가 있으면 이름·한글명·의미를 맞추고, 결정 기록 문서가 있으면 승인된 주요 변경의 이유와 결정을 기록한다.

## 구조와 확장

- 기본 묶음은 `개념[]`, `관계[]`, `소스[]`다. 종류와 개수는 프로젝트에 맞게 정한다.
- `이름`은 영문 snake_case 식별자이고 `한글명`은 필수다. 개념 이름과 최상위 소스 이름은 각 목록에서 고유하게 정한다.
- 명세가 있는 개념은 `명세문서`에 프로젝트 루트 기준 경로를 기록한다. 정본 상단에는 작업에 필요한 엔티티의 명세만 먼저 읽으라는 안내를 유지한다.
- 프로젝트에 필요한 태그·속성·하위 구조를 확장할 수 있다. 기존 이름과 참조의 의미를 유지하며, 확장도 사용자 통제 절차를 따른다.
- 템플릿의 `?`는 생략 가능한 속성 표기다. 실제 문서에서는 사용하는 키의 `?`를 제거하고 필요한 항목을 채운다.

## 소스 선정

- 소스는 DB·문서·파일 등 실제 데이터 단위로 정의한다. 개념 내부 소스의 `이름`은 최상위 소스의 `이름`을 그대로 참조한다. 별도의 `소스명`을 만들지 않는다.
- 개념의 정본은 정보 범위별로 구분한다. 단가와 유급 시수를 각각 다른 원본에서 관리하면 둘 다 기록한다.
- 동기화 사본은 해당 개념의 특정 정보를 실제로 먼저 확인하는 경우에만 `참고본`과 `우선 탐색 대상`으로 등록한다. 개념마다 역할을 따로 판단하고 범위·조회 조건만 짧게 적는다. 같은 정보가 다르면 정본을 따른다.
- 단순 언급·근거 자료·실행 상태는 그 자체가 개념의 정본이거나 우선 조회본인 경우에 개념 소스로 등록한다. 필요한 근거 위치와 접근 방법은 최상위 소스 정의에서 찾게 한다.

## 동기화

- 개념의 `동기화`에 `원본`·`대상`·`방법`을 기록한다. `원본`은 해당 개념의 소스 이름이다. `대상`은 해당 개념의 소스로 등록된 경우 소스 이름을 쓰고, 그 외에는 실제 위치를 적는다. 상대 파일 경로는 프로젝트 루트를 기준으로 한다.
- 단순 갱신 결과물은 동기화 지시에서 위치와 갱신 절차를 찾을 수 있게 한다. 어떤 개념에서도 우선 조회에 쓰이지 않는 사본은 최상위 소스에도 등록 대상에서 제외한다.

## 관계 이름

- 관계의 주체·대상은 개념 이름을 참조하고, 관계는 방향이 분명한 동사로 적는다. 대상이 여러 개면 관계를 나눠 적는다.
- 관계 이름은 주체가 대상에 대해 하는 일과 대상이 바뀌거나 사라질 때 무엇을 처리해야 하는지를 드러내도록 고른다. `연결된다`, `근거한다`, `뒷받침한다`처럼 여러 뜻으로 쓰일 수 있는 이름은 실제 자료와 운영 방식을 확인한 뒤 더 구체적인 후보와 비교한다.
- 의미가 다른 후보는 서로 바꿔 쓸 수 있는 동의어로 제시하지 말고 적용 조건과 운영상 차이를 함께 적는다. 예를 들면 다음과 같다.
  - 할 일 → 강의: `종속된다`는 강의가 삭제될 때 할 일도 함께 정리하는 정책일 때 쓴다. `후속 조치다`는 강의에서 생긴 일이지만 작업 이력을 별도로 보존할 때 쓴다.
  - 협의·자료 → 회차: `회차 일시를 명시한다`는 자료에 회차 날짜와 시간이 적혀 있을 때 쓴다. `일정 변경을 통보한다`는 기존 일정과 달라진 내용을 알리는 자료에 쓴다.
  - 협의·자료 → 정산: `지급 조건을 명시한다`는 금액·단가·지급 기준을 적은 자료에 쓴다. `합의 내용을 증빙한다`는 실제 합의를 확인할 수 있는 자료에 쓴다.
- 프로젝트 용어와 확인된 관계에 맞게 이름을 제안한다. `운영한다`처럼 의미가 이미 분명한 이름은 유지할 수 있다. `종속된다` 같은 관계명은 삭제 정책을 그 자체로 확정하지 않는다. 실제 삭제·보관·참조 해제 방식은 확인한 정책에 따로 기록하고, 미정이면 이름 변경안의 확인 사항으로 남긴다.

## 유형별 필수 위치 정보

최상위 `소스[].소스정보`는 필수이며 실제 문서에서 빈 사전으로 남기지 않는다. 이름·서비스명·용도 설명만으로 위치를 대신하지 않는다. 다음 중 해당 소스 유형에 필요한 정보를 기록한다. 모든 유형을 프로젝트에 구성할 필요는 없다.

| 소스 유형 | 필수 정보 |
| --- | --- |
| 로컬 파일 | 실제 파일 경로. 상대 경로라면 기준 디렉터리도 명시한다. |
| 파일 묶음 | 실제 디렉터리·경로 패턴·변수의 의미. 사용한 파일이 그 패턴에 포함되는지도 확인한다. |
| Notion DB | 확인한 DB URL, `database_id`, 조회에 사용하는 `data_source_id`. |
| Notion 페이지 | 페이지 URL, `page_id`, 필요한 본문 섹션. |
| Drive 파일 | 파일 URL과 `file_id`. 접근 계정이 구분에 필요하면 계정도 적는다. |
| 메일 | 계정, 메시지 URL 또는 메시지 ID. |

고정 위치가 아닌 연결 자료는 실제 URL·ID가 저장된 문서의 경로·섹션·필드까지 특정한다. 확인하지 못한 위치는 추정하거나 예시 값으로 채우지 않는다. 필요한 근거를 확인하거나 사용자에게 확인할 항목을 제시한다. 소스 발견과 위치 확인만으로 등록·변경 동의를 받았다고 간주하지 않는다.

DB 필드명·자료형·API 제약은 소스별 기술 문서에서 유지하고 필요한 위치에서 링크한다.

## 초기화

프로젝트 온톨로지를 설치·구축하거나 기존 정본을 에이전트 지침에 연결할 때 프로젝트 루트에서 도우미를 실행한다.

~~~bash
python path/to/ontolog/scripts/init_ontology.py --project-root .
~~~

도우미는 기존 `AGENTS.md` 또는 `AGENTs.md`에 온톨로지 참조 지침을 추가한다. 둘 다 없으면 프로젝트 루트에 `AGENTS.md`를 만든다. 기존 정본은 보존하며, 새 정본의 빈 목록은 구성의 출발점이다.

완료 전에 에이전트 지침에서 `ONTOLOGY.yaml`로 이어지는 프로젝트 상대 링크와 모든 프로젝트 작업을 시작할 때 정본 전체를 읽으라는 안내를 확인하고 빠진 항목을 보완한다. 구축 중 엔티티 명세를 추가했다면 도우미를 다시 실행해 링크를 연결한다.

## 사용자 통제

- 온톨로지의 신규 내용과 개념·관계·소스·속성의 추가·수정·삭제, 이름·구조·서식 변경은 사용자가 직접 구체적으로 지정하거나 명시적으로 승인한 범위에서만 반영한다. 오탈자·서식 수정도 예외가 아니다.
- 사용자가 직접 지정하지 않은 변경은 이유, 변경 전후 내용, 영향을 제시하고 동의를 받는다. 동의 전에는 기존 정본을 유지하고, 제안은 대화나 별도 초안에서 검토할 수 있게 한다.
- 특히 강의 프로젝트의 관계명 변경은 이유, 변경 전후 이름, 예상 영향을 구체적으로 제안한다. 사용자가 지정하거나 승인한 범위에만 반영한다. 대상 삭제 시 할 일을 함께 정리할지, 이력을 보존할지, 참조만 해제할지 확인되지 않았으면 그 운영 정책을 확인 사항으로 표시한다.
- 무응답, 추정, 새 사실이나 구조의 발견, 일반적인 관리·정리 요청, 과거의 포괄적 위임을 변경 동의로 간주하지 않는다. 승인 범위를 넓히려면 별도 동의를 받는다.
- 이미 구체적으로 요청되거나 승인된 동일 범위에 대해 다시 승인을 요구하지 않는다. 그 범위만 반영하고 프로젝트의 추가 관리 규칙도 지킨다.
- 스킬 실행, 초기화, 일반 문서 도우미의 `--force`, 참조자료 변경은 기존 정본을 덮어쓰거나 자동 정규화하는 근거가 아니다.

## 검증 기준

- **구조**: YAML 문법과 템플릿의 필수 항목을 확인한다. 이름은 목록 안에서 고유하고 한글명이 있으며, 프로젝트 확장 속성은 임의로 금지하지 않는다.
- **참조**는 개념의 소스가 최상위 소스를 가리키고, 관계의 주체·대상이 기존 개념이며 관계명이 실제 동작을 나타내는지 확인한다. 동기화의 원본과 소스로 등록된 대상은 개념의 소스로, 그 밖의 대상은 파일 경로나 주소로 확인한다. 개념의 명세 경로가 실제 파일을 가리키고 파일명이 개념의 영문 이름과 일치하는지 확인한다.
- **접근성**: 소스 유형에 맞는 실제 경로·URL·식별자가 있고, 그 정보로 같은 원본을 다시 찾을 수 있는지 확인한다. 자리표시자·예시 값이나 확인하지 않은 위치는 정본에 확정값처럼 두지 않는다.
- **소스 선정**은 각 소스의 관리 범위와 사본의 우선 탐색 용도를 확인한다.
- **통제**: 정본·참고본의 역할이 모순되지 않고, 변경 내용이 사용자가 지정하거나 승인한 범위에 한정되는지 확인한다.

## 검증 절차

1. 변경 전후를 비교해 요청·승인 범위 밖의 수정이 없는지 확인한다.
2. 변경한 항목의 구조와 영향을 받는 참조를 대조한다. 전체 검증을 요청받으면 정본 전체의 구조와 참조를 확인한다.
3. 파일 경로는 실제 파일을 확인하고, 외부 소스는 가능한 읽기 전용 조회로 주소·ID를 대조한다. 확인할 수 없는 항목은 미검증으로 남긴다.
4. 검증 결과와 미검증 항목을 보고한다. 발견한 오류는 승인된 범위에서만 고치며, 그 밖의 수정은 별도 변경안으로 제시한다.
